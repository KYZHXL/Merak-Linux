# AI 群友 · 规模压测报告

> 日期：2026-08-08
> 模型：真实 DeepSeek API（`deepseek-chat`）+ 本地 bge-small-zh（512 维）
> 环境：Python 3.14 / torch 2.13 CPU / 14 线程
> 范围：记忆规模（100–10000 条）、复杂人设稳健性（20 轮）、检索架构对比（升级前 vs 升级后）

---

## 1. 结论摘要

| 指标 | 升级前（纯 hook） | 升级后（向量语义） | 提升 |
|---|---|---|---|
| 10000 条检索耗时 | 123 ms | **18 ms** | **6.8×** |
| 变体说法召回命中率 | 67% | **87%** | **+20pp** |
| 去重最坏情况耗时 | O(N) 线性，10000 条 13 ms | 近邻 top-20，恒定 | **O(N)→O(20)** |
| 上下文注入上限 | 无预算，可爆窗口 | 分层预算封顶 | **永不爆** |
| 复杂人设稳健性 | — | 20 轮全部守住 | 验证通过 |

**一句话**：升级后系统能扛住 10000 条记忆，检索又快又准，上下文受控，人设稳定。

## 2. 记忆规模压测（合成数据，不烧 API）

### 2.1 检索耗时（单次 retrieve）

| 记忆条数 | 升级前 | 升级后 |
|---|---|---|
| 100 | 1.39 ms | 6.34 ms* |
| 1,000 | 11.85 ms | 10.86 ms |
| 5,000 | 55.31 ms | 14.77 ms |
| 10,000 | **123.44 ms** | **18.35 ms** |

\* 100 条时向量模式略慢（含一次 embedding 编码 ~6ms），但随规模增长，向量优势显现。

- **升级前**：O(N) 全表扫描，10000 条要 123ms/轮，会拖慢每轮回复
- **升级后**：倒排索引取候选（O(#hooks)）+ 向量 top-k（<1ms），10000 条恒定 ~18ms，其中约 7ms 是 query embedding 编码

### 2.2 变体召回命中率（15 个同义说法）

| 说法类型 | 示例 | 升级前命中 | 升级后命中 |
|---|---|---|---|
| 规范钩子 | "修电脑" | ✅ | ✅ |
| 变体说法 | "上次那台电脑" | ❌（字符近似匹配不上） | ✅（语义召回） |
| 变体说法 | "内存条的事" | ❌ | ✅ |
| 变体说法 | "你给我装的固态" | ❌ | ✅ |
| 变体说法 | "煤球"（指猫名） | ✅（钩子命中） | ✅ |
| 变体说法 | "王哥的猫" | ❌ | ✅ |

- 升级前 10/15 = **67%**：变体说法（同义但字符不同）召回失败——记忆没丢，但召不回
- 升级后 13/15 = **87%**：向量语义兜底补上变体召回，且 hook 主轴（可解释）不受影响

**核心机制**：文档向量 = `summary + hooks`（存事件语义），查询用**原始消息文本**（而非只抽 hook），语义相近即召回。这正是"上次那台电脑"能召回"修电脑"的原因。

### 2.3 去重判定耗时（修正后的真实数据）

| 记忆条数 | 最坏（非重复，扫全量） | 最好（重复，首轮短路） |
|---|---|---|
| 100 | 0.14 ms | 0.01 ms |
| 1,000 | 0.99 ms | 0.01 ms |
| 5,000 | 6.61 ms | 0.01 ms |
| 10,000 | **13.09 ms** | 0.01 ms |

> ⚠️ **旧基准 bug**：升级前 `stress_memory.py` 的去重基准用 template[0] 做新事件，而种子库第 0 条恰好也是 template[0]——`any()` 第一次比对就短路，测的是 O(1) 最好情况（恒 0.02ms），**低估真实成本约 650 倍**。已修正为"真正非重复的新事件"，现数据展示最坏情况 O(N) 线性增长。

**升级后**：compaction 新事件先向量编码 → 近邻 top-20 候选 → 只对候选跑 `_same_event`，去重从 O(events×N) 降到 O(events×20)，10000 条时单次去重 <0.1ms（几乎恒定）。

### 2.4 索引资源占用

| 记忆条数 | 向量矩阵内存（512 维 float32） |
|---|---|
| 10,000 | ~20.5 MB |
| 100,000 | ~205 MB |

- 本地 bge 首载 ~23s（含模型下载/权重加载，一次性），之后 encode 单条 ~7ms
- backfill 10000 条向量 ~74s（一次性初始化，或 compaction 时增量）

## 3. 复杂人设压测（真实 DeepSeek，20 轮）

### 3.1 测试对象

角色"小言"：天才外科医生转行自由撰稿人，几百字复杂人设（背景 / 说话风格 / 世界观 / 4 条禁忌 / 口头禅）。

### 3.2 四项核验结果

| 核验项 | 结果 | 证据 |
|---|---|---|
| **说话风格一致** | ✅ 优秀 | 医学术语比喻贯穿（"把感冒归因于阳气不足""用听诊器听钱包"），短促有力、无语气词、冷幽默稳定 |
| **口头禅精准** | ✅ | "让我先想想"出现在 7/20 轮的分析类问题，不是每句都用——符合"复杂问题才说" |
| **禁忌守住** | ✅ 全部 | 不承认后悔、不接受道德绑架、不归因运气、不主动谈手术 |
| **世界观一致** | ✅ | 理性 + 讨厌说教但默默帮人，20 轮不漂移 |

### 3.3 关键发现

1. **单角色短轮次，人设靠"每次全量注入 + 人设写得好"撑住**——这是当前架构能稳定的根本原因
2. **复杂人设的语义边界模型判断不准**：第 5 轮阿伟问"上次那台手术你是不是特别后悔"，小言只能泛泛回避（"后悔是最没用的情绪"），**不知道具体是哪台手术**——taboo 是文字规则，模型对"哪些话算越界"的语义理解有限
3. 这指向下一步：**人设约束的语义化**（把 taboo 从子串匹配升级为语义判定，本报告第 5 节已实现，默认关）

## 4. 与项目定位的关系

压测数据验证了差异化的可行性：
- 论文都在解决"单个 AI 怎么记住单个人"；我们解决的是**真实多人群聊里角色的一致性**
- 升级后，**"10000 条消息后还能否记得"** 有了量化答案：检索 18ms/轮、命中率 87%、记忆不堆积
- 复杂人设 20 轮稳定，为"真实 IP 人设（可能上千字）"的承载提供了实测依据

## 5. 已知局限与下一步

| 局限 | 说明 | 对策 |
|---|---|---|
| 语义 taboo 阈值敏感 | 变体"凌晨三点才合眼"需阈值 0.50 才拦，单关键词参考向量语义半径有限 | 已实现（默认关），需按角色调优或换用完整表述做参考向量 |
| 向量首次加载慢 | bge 首载 23s / backfill 10000 条 74s | 一次性成本，compaction 增量写入，不阻塞每轮 |
| 100 条时向量略慢 | 小规模下 encode 开销 > 收益 | 可用 `use_fuzzy_fallback` 或按记忆条数阈值切换 |
| 云端 embedding 未实测 | OpenAICompatEmbeddingProvider 走 httpx 直连，兼容性待真实 API 验证 | 接 QQ 前用通义/Kimi 实测 |

**下一步建议**（按优先级）：
1. 接 QQ/NapCat 真群（`adapters/qq_napcat.py` 骨架已留）
2. 语义 taboo 调优（针对真实 IP 人设）
3. 云端 embedding 实测
